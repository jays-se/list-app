## Decisions

| Decision | Why | Recorded in |
|---|---|---|
| Approval applies the change through the same functions as a direct edit (`updateTx`, `replaceSetTx`, `createTx`, checklist and attachment `*Tx`), in one transaction with the decision | One validation and history path; nothing is half-applied | ADR-0023 |
| "Stale" means the request's precondition no longer holds, not a whole-task version check | Comments and other edits would otherwise reject nearly every approval | ADR-0023 |
| Flat request payload, validated per kind; the server writes the `summary` sentence | The in-house generator has no discriminated unions; one sentence is reused by history, inbox and UI | ADR-0023 |
| Decision routes are at `/api/v1/requests/{id}/…` | Same ServeMux ambiguity as attachments in Sprint 3 | ADR-0023 |
| `ATTACHMENT_ADD` requests deferred | They need staged uploads that aren't attached until approval | ADR-0023, open items |
| Transactional outbox with `SKIP LOCKED`, handlers in savepoints, backoff up to 1 h, 10 attempts | Safe across instances; no lost or phantom side effects | ADR-0023 |
| Notifications are idempotent through `UNIQUE (user_id, dedupe_key)` | Redelivery is harmless | SCHEMA_DOC |
| DUE runs hourly for tasks due tomorrow (UTC), one notification per task per day | Simple and restart-safe; time zones are an open item | ADR-0023 |
| Notification text: the server sends a `detail` fragment and the worker adds the actor's name | Keeps English strings in one place per layer, with no formatting in React | notifications VM |
| Request-mode checkboxes are **controlled** (unlike manage mode) | A toggle only files a request, so the box must snap back to the saved state | ChecklistSection |

## Delivered
- **API:**
  - migration 0005: `change_requests`, `outbox`, `notifications` and `notification_settings`
  - `internal/outbox`: `Emit` and `Dispatcher`
  - the task service refactored into `*Tx` helpers, plus the request engine and its routes
  - a notification module: consumers, DUE scheduler, inbox API and settings API
  - `app.Build` returns the background workers, and `main` starts them
- **Contract:** request and notification paths and schemas; `viewer.canRequest`, `counts.pendingRequests`, `task.requests`, and `REQUEST_*` event kinds
- **Worker:**
  - views: `inbox.list`, `inbox.badge`, `notifications.settings`; `tasks.detail` gains request mode, requests, pending markers and the session user
  - actions: `requests.submit` (one request per change), `requests.propose`, approve, reject and withdraw, and optimistic `notifications.*`
- **Web:**
  - `RequestForm`, the note dialog and `RequestsSection`
  - request mode in the checklist, subtask and attachment sections
  - `/inbox` with filters, mark read, deep links and settings
  - the nav unread badge
