# 2026-09-30 · Workspace owners manage all tasks; Sprint 3

## What the requester asked
> "Yes workspace owner can edit any task, and start sprint 3"

## Decisions

| Decision | Why | Recorded in |
|---|---|---|
| **Workspace owners can manage every task, including its owners** | Requester's answer to the open question in ADR-0020 | ADR-0021 (supersedes ADR-0020 in part) |
| Blob storage behind one interface: a **local** driver (default) and an in-house **S3 SigV4** driver | No Docker or cloud yet; no SDK for four calls; e2e runs anywhere | ADR-0022 |
| Attachment routes live at `/api/v1/attachments/{id}`, not under `/tasks/attachments` | The reference app's path is ambiguous in Go's ServeMux against `/tasks/{id}/history` | ADR-0022 |
| Subtasks are one level deep; deleting a parent deletes its subtasks | Matches the reference; keeps the model simple | SCHEMA_DOC |
| Client delete is workspace-owner only and unlinks tasks | Consistent with labels; reference behaviour | E8-S1 |
| Checklist, comments and attachments don't bump the task `version` | So they don't cause 409s on concurrent field edits | tasksvc |
| Mentions are picked, not parsed; the worker keeps only those still in the text | Reliable, with no fragile name parsing | `comments.add` |
| Optimistic checkboxes are uncontrolled and keyed on the worker's value | The same flicker as the Sprint 2 filters, found by e2e | skill `add-worker-action` |
| Row pluralization moved into the worker ("1 comment · 1 file") | Screenshot showed "1 comments"; pluralizing in React broke the render-only rule | TaskRowVM `activityText` |

## Delivered
- **API:**
  - Clients module.
  - Tasks gain a client link, subtasks and counts.
  - Checklist, comments with mentions, attachments (reserve, PUT, complete, redirect download, delete, 5×5 MB limits).
  - History events and status stages, written in the same transaction as each change.
  - `blobstore` (local and S3), the `signed` package, `apperr` everywhere.
  - Migration 0004 with RLS.
- **Worker:**
  - Views: `tasks.history`, `clients.list`, `clients.detail`, and detail/list extensions.
  - Actions: `tasks.addSubtask`, `checklist.*` (optimistic), `comments.add`, `attachments.upload` (XHR progress pushes) and `attachments.delete`, `clients.*`.
  - Protocol push `upload.progress`; context gains `upload` and `notify`.
- **Web:**
  - The drawer gains Details and Activity tabs, with Subtasks, Checklist, Attachments and Comments sections.
  - Client field and filter.
  - Clients pages.
  - ui-kit `Tabs`.

## Verification (run locally)
- **Unit tests:** 252 Vitest tests pass. Among them:
  - uploads through the real kernel (size and count limits, progress sequence)
  - mention filtering
  - an optimistic toggle rolling back on a 500
  - history sentences and time in status
- **Go tests:** all pass with `-race` against Postgres, at **79.3%** statement coverage. The S3 driver's live paths run only when `TEST_S3_ENDPOINT` is set. They include:
  - the full attachment lifecycle through the local driver
  - cross-tenant 404s
  - clients unlinking tasks and subtask cascades
  - the history event kinds and stages
  - a workspace owner managing another person's task
  - the AWS SigV4 known-answer test
- **E2E:** 13 Playwright tests pass on three consecutive runs. They cover:
  - clients
  - subtasks
  - the optimistic checklist
  - a comment with a highlighted mention from a second person
  - a **real file upload and download** plus a rejected 5 MB+1 file
  - the Activity tab
  - axe on the drawer, the Activity tab and the client pages

## Not verified / still open
- **S3 driver against a real server:** downloading MinIO failed twice with a network error.
- **One flaky run:** the very first e2e run reported an axe violation on the client detail page, and it didn't reproduce in the next three runs. Watch for it in CI.
- **Deferred to E12:** a cleanup job for PENDING attachment slots that are never completed.
- **Carried over:** Google credentials, Docker, a GitHub remote, data retention and audit requirements, and the brand colour.
