# E4 Tasks core

> Mirrors docs/mvp-plan.md §8. Global Definition of Done: docs/definition-of-done.md. Format: ID · Title · Priority · Complexity · Deps.

- **E4-S1 · Tasks API CRUD and filters** · P0 · L · Deps: E2-S3, E3-S3
  - **Status:** Done (Sprint 2). The API covers list with filters (status, mine, assigneeId, labelId), get, create, PATCH with only the fields sent plus If-Match (428/409), and delete; validation matches the reference messages; migration 0003 with RLS. Flow tests run on Postgres. **Deferred:** the `clientId` and `parentId` filters, with clients and subtasks in Sprint 3.
  - Endpoints: `GET /tasks` (status, mine, assigneeId, labelId, clientId, parentId), `GET/POST/PATCH/DELETE /tasks/:id`.
  - Validation: title is required; start and end dates are required on create; the end date must not be before the start date.
  - Other behavior: `version` field and ETag; `viewer` flags computed by policy.
  - AC: all validations return 422 problem+json with field `errors[]`.
- **E4-S2 · Task list view (worker VM and UI)** · P0 · L · Deps: E4-S1, E1-S5
  - **Status:** Done (Sprint 2). The `tasks.list` view groups by status in the worker, with due-date tones and filter options; filters live in the URL (uncontrolled and URL-keyed); it polls every 15 s and keeps the previous result while filters load. A 2,000-task view model builds in under 100 ms (unit perf test). **Not done:** a React frame-time trace for 2k rows, and virtualization if a trace shows it's needed.
  - Description: the `tasks.list` VM (filter chips from the URL, grouping by status, counters) with 15 s polling.
  - AC: filters live in the URL; the VM is computed in the worker; the list renders in under 16 ms per frame for 2k tasks (perf test).
  - Tasks: extract the `add-feature` skill (it chains the pattern skills), and the `write-e2e-test` skill if it doesn't exist yet.
- **E4-S3 · Task create** · P0 · M · Deps: E4-S2
  - **Status:** Done (Sprint 2). A create drawer at `?create=1`; the worker validates with the API's messages and nothing is sent when invalid.
  - Description: the `tasks.create` action; validators are shared through `@app/domain` and run in the worker.
  - AC: the reference's validation messages are shown; the list refreshes after create.
  - Tasks: extract the `add-worker-action` skill.
- **E4-S4 · Task detail drawer and manager edit** · P0 · L · Deps: E4-S3
  - **Status:** Done (Sprint 2). A detail drawer at `?task=<id>` that polls every 10 s; `tasks.save` diffs the draft in the worker and PATCHes only the changed fields with If-Match; a discard guard; on 409, a "Reload latest" button; delete with confirmation; read-only view for people who can't manage.
  - Description: `?task=<id>` opens the drawer; the `tasks.detail` VM polls every 10 s; saving PATCHes only changed fields (diff computed in the worker); discard guard.
  - AC: a 409 conflict shows reload/merge options.
- **E4-S5 · Assignees, owners and labels** · P0 · M · Deps: E4-S4
  - **Status:** Done (Sprint 2). PUT for assignees, owners (creator only; the creator is filtered out) and labels; members and labels are validated per workspace; changes are sent only when a set changed.
  - Endpoints: `PUT /tasks/:id/assignees`, `PUT /tasks/:id/owners`, `PUT /tasks/:id/labels`.
  - AC: only `canManageOwners` can change owners; the creator is excluded from the owner list.
- **E4-S6 · Subtasks** · P1 · M · Deps: E4-S4
  - **Status:** Done (Sprint 3). Subtasks one level deep, created from the parent drawer; list rows show "Subtask of …" and "n/m subtasks"; deleting a parent deletes its subtasks.
  - AC: subtask done/total counters are shown on the parent.
- **E4-S7 · Checklist** · P1 · M · Deps: E4-S4
  - **Status:** Done (Sprint 3). Checklist add, rename, check, (un)assign and remove, with the optimistic toggle and rollback in the worker (tested).
  - Endpoints: `POST /tasks/:id/checklist`; `PATCH` and `DELETE /tasks/checklist/:itemId`.
  - Supports assigning items; optimistic toggle.
- **E4-S8 · Comments and mentions** · P1 · M · Deps: E4-S4
  - **Status:** Done (Sprint 3). Comments from any member; mentions are picked from members and the worker keeps only those still in the text; mentions are highlighted; stored in `comment_mentions`. MENTION notifications shipped in Sprint 4 (E9-S1).
  - AC: the mention picker lists workspace members; a mention creates a MENTION notification (E9).
- **E4-S9 · Attachments** · P1 · M · Deps: E2-S5, E4-S4
  - **Status:** Done (Sprint 3). The worker checks the 5 MB and 5-file limits, reserves a slot, PUTs with XHR progress pushes, then confirms (server-side size check); download by redirect; delete. e2e covers a real upload and download and the oversize rejection.
  - Description: the worker reads the file, checks size, uploads with the presigned PUT and reports progress through push.
  - AC: messages for "X is larger than 5MB" and "Could not read attachments".
